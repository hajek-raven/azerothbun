# AGENTS.md

This repo is a 1:1 TypeScript port of [AzerothCore](https://github.com/azerothcore/azerothcore-wotlk) on Bun. The client is World of Warcraft **3.3.5a (build 12340)**.

`azerothcore/` is the C++ and SQL reference. Do not build or run it from here. The server that runs is `src/`.

## Port the whole topic

When a topic is in scope, port it completely. A half-baked slice that only covers the packets or columns needed for the current demo is not a port.

A topic is one AzerothCore system (auth, characters, creatures, game objects, items, spells, quests, and so on), including the tables, loaders, and server behavior that system owns.

- Read the C++ and the SQL in `azerothcore/` before writing the TypeScript.
- Bring over the full behavior of that system, not a stub that is "enough to log in" or "enough to spawn one row."
- Related tables that the system reads belong in the same port. Do not leave them for a later pass.
- Wire the data through types, queries, and packets. A column that exists only in MySQL and is never loaded is unfinished.
- Behavior that the client never sees yet still gets stored and loaded. The schema and the data path come first; feature flags do not justify dropping fields.

## SQL

The databases are MySQL, exactly as in AzerothCore: `acore_auth`, `acore_characters`, and `acore_world`. `docker compose up -d` starts a local MySQL 8.4 (`docker-compose.yml`, user `acore` / `acore`). The server connects with `LoginDatabaseInfo`, `CharacterDatabaseInfo`, and `WorldDatabaseInfo` from `configs/worldserver.conf`.

The schema is never written by hand. `src/database/updater.ts` (port of `DBUpdater` / `UpdateFetcher`) fills an empty database from `sql/base/db_*/` (a copy of `azerothcore/data/sql/base/`) and then applies every file from `azerothcore/data/sql/updates/` listed in `updates_include`, recorded in `updates` like the C++ does. The server runs it at startup; `bun run db:update` runs it alone.

- Do not write `CREATE TABLE` or `ALTER TABLE` in `src/`. A missing column means a missing update file, not a code change.
- Keep AzerothCore table and column names everywhere, including in TypeScript row types. Do not alias `id` to `entry` or `curhealth` to `health` in queries.
- Do not drop a column because the current packet or the current feature does not read it.
- `src/database/schema/{auth,characters,world}.ts` is generated by `bun run gen:db-schema` (`drizzle-kit pull` on the live databases). Regenerate it after `db:update` brings in new updates. Never edit it.

Queries use drizzle-orm (`1.0.0-rc.4`) on `Bun.SQL` (`drizzle-orm/bun-sql/mysql`):

- `acore_world` is read once at startup into `WorldTables` (`src/database/world-tables.ts`), the way `ObjectMgr` and the other managers cache it. Game code reads world rows synchronously with `all`, `where`, and `first`. A table read at runtime must be listed in `src/database/world-table-list.ts`.
- `acore_auth` and `acore_characters` are queried with `await`. Their pools have one connection, so writes queued with `executeAsync` (the `CharacterDatabase.Execute` pattern, for code that cannot wait, like the world tick) stay in order before later reads.
- Guids come from `objectGuids` (`src/game/globals/object-guids.ts`, `ObjectMgr::SetHighestGuids`). Tables that AzerothCore gives no `AUTO_INCREMENT` (`characters`, `item_instance`, and the rest) never rely on the database for ids.
- Tests use `testDatabase("characters" | "auth")` or `seededTestDatabases()` from `src/database/test-db.ts` (throwaway `acore_test_*` databases as MySQL user `acore_test`) and `WorldTables.fromRows` or `worldFromSql` for world rows.

The spawn list the server shows follows `ObjectMgr`, `GameEventMgr`, and `PoolMgr`:

- Import every map. Do not clip spawns to a coordinate box. In this dump `creature.zoneId` and `areaId` are 0, so they cannot locate Northshire or anything else.
- A stored `phaseMask` of 0 is shown as 1. Keep `spawnMask` and `phaseMask`, including dungeon bits. Do not drop a row because it is not phase 1 or spawn-mask bit 0.
- A positive `game_event_creature`, `game_event_gameobject`, or `game_event_pool` id is not in the default spawn set. Negative event ids stay visible (they are present while the holiday is off). Rows with no event stay. The hidden rows remain in the database.
- A pool shows `pool_template.max_limit` members. `0` means no limit. Sort by chance descending, then guid ascending. The other members remain in the database.
- Hide a creature spawn whose template is missing, or whose `creature_template_model` rows have no `CreatureDisplayID` > 0. Keep the template anyway.
- Hide a gameobject spawn whose template is missing or whose `displayId` is 0. Keep the template anyway, including `displayId` 0.

Display ids are `creature_template_model`, not columns on `creature_template`. Bounds and gender are `creature_model_info`. Equipment is `creature_equip_template`. Spawn entry is `creature.id` (update `2026_06_16_00` renamed `id1` and dropped `id2`/`id3`). `curhealth` and `curmana` stay those columns.

## Bun

Use Bun. Do not use Node.js, npm, pnpm, yarn, or Vite.

- `bun <file>` instead of `node` or `ts-node`
- `bun test` instead of Jest or Vitest
- `bun install` instead of npm, yarn, or pnpm
- `bun run <script>` and `bunx <package>` instead of npm scripts and npx
- Bun loads `.env`. Do not use dotenv.
- `Bun.listen` for the auth and world sockets. Do not use Node `net` or the `ws` package.
- `Bun.SQL` for MySQL, through `drizzle-orm/bun-sql/mysql`. Do not add `mysql2`, `better-sqlite3`, or another driver.
- `Bun.CryptoHasher` for hashes. Do not pull in extra crypto packages.
- `Bun.file` instead of `node:fs` readFile / writeFile.
- Do not use Node `Buffer`.

Tests live next to the code and run with `bun test`. API details are in `node_modules/bun-types/docs/**.mdx`.
